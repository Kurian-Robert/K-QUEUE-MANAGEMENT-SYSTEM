Relational Schema & 3NF Normalization Proof

The KQMS database schema contains 8 normalized relational entities with rigorous integrity constraints, eliminating data anomalies while preserving dependencies.

office Table
PK office_id INT (Auto)
office_name VARCHAR(80)
office_type VARCHAR(40)
district VARCHAR(40)
department Table
PK department_id INT (Auto)
department_name VARCHAR(100)
FK office_id CASCADE
service Table
PK service_id INT (Auto)
service_name VARCHAR(60)
avg_service_min CHECK (> 0)
FK department_id CASCADE
staff Table
PK staff_id INT (Auto)
staff_name VARCHAR(60)
role VARCHAR(30)
FK department_id CASCADE
citizen Table
PK citizen_id INT (Auto)
citizen_name VARCHAR(60)
phone VARCHAR(15)
email UNIQUE
queue_token Table
PK token_id INT (Auto)
token_number VARCHAR(20)
status CHECK (Status)
FK citizen_id CASCADE
FK service_id CASCADE
FK staff_id SET NULL
feedback Table
PK feedback_id INT (Auto)
FK token_id UNIQUE
FK citizen_id CASCADE
rating CHECK (1-5)
comments TEXT
admin Table
PK id INT (Auto)
username UNIQUE
email VARCHAR(50)
password HASHED

Academic Normalization Proof Summary

  • 1NF: Every attribute contains only atomic, single-valued items; unique primary keys exist on all relations.
  • 2NF: Schema satisfies 1NF, and all non-key attributes are fully functionally dependent on the entire primary key (since single-column surrogate keys are used, partial dependency is strictly impossible).
  • 3NF: Schema satisfies 2NF and contains no transitive functional dependencies ($X \to Y$ and $Y \to Z$). Token attributes reference Service directly rather than transitively replicating Department or District data. Feedback is isolated into its own entity.
